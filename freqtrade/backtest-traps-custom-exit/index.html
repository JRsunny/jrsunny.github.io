在这篇文章中，我将解释为什么你在 freqtrade strategy 上使用 custom_exit 函数时需要小心。让我们从这个简单的 custom_exit 逻辑开始

逻辑非常简单，当交易至少有 5% 的利润时，交易会以 “roi_reached” 的 exit tag 退出。在 dry/live run 中，会发生的情况是每隔 throttle secs（默认是 5 秒，除非你设置了不同的值），机器人会从交易所获取当前 rate 并计算 current_profit，然后将该值提供给上面的 custom_exit 函数。

backtest 的陷阱在于，为了让 backtest 更快，并且因为没有 K线内变动的数据，custom_exit 函数只会在 K线的 open rate 上被检查，这意味着 current_profit 值也只会每根 K线检查一次。为什么这会有问题？让我们看看下面 backtest 逻辑的例子。

假设你在 K线 A 上开了一笔 BTC/USDT 币的交易。接下来发生的是，机器人使用 K线 A 的 open 值来计算 current_profit，并将其提供给上面那样的 custom_exit 函数。由于 current_profit 仍然低于 5%，机器人移动到 K线 B 并重复相同的过程（使用 K线 B 的 open rate 来计算 current_profit，并将该值发送给 custom_exit 函数）。

让我们前进到 K线 F。如果我们基于 K线 F 的 open rate 计算利润，利润仍然低于 5%。但接着，如果你看 K线 F 的全部值，它是一根绿色 K线，其中 close 值相比 open 值是 10%。这意味着在 dry/live run 的情况下，交易会在 K线 F 中间的某个位置以 5% 的利润退出。但对于 backtest，由于 K线 F 的 open 处 current_profit 仍然低于 5%，机器人前进到 K线 G，此时 K线 G 的 open 处 current_profit 是 15%。发送给 custom_exit 函数的值触发了逻辑，并以 15% 的利润退出了交易。在这种情况下，backtest 与 dry/live 的差异是 15% 对 5% 的利润。这是一个显著的差异。所以下一个问题是

如何避免这些陷阱？
我用来避免它的方法有三种，分别是

  1. 完全不要使用 current_profit
  2. 基于上一根 K线的 close 值来计算 current_profit。所以对于上面的例子，不要使用 K线 F 的 open rate，而是使用 K线 E 的 close rate 来计算 current_profit。这将确保 backtest 和 dry/live run 会相似。这种方法的问题是你不会在 dry/live run 中有 K线内退出，因为无论 K线 F 的当前 rate 是什么（每隔 throttle secs 获取一次），current_profit 将始终保持不变（锚定在 K线 E 的 close rate 上）
  3. 使用 timeframe-detail 来帮助最小化影响。但由于目前可用的最低可工作 timeframe 是 1 分钟 timeframe，这意味着如果你有一根非常长的 1 分钟绿色 K线，它仍然容易受到这种陷阱的影响。但一般来说，差异不应该像你不使用它时那么大。
